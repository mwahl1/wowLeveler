# P2 Guide Engine: technical specification

Status: **draft for review**. Nothing in this document is implemented yet.
P0 remains pending in-game verification. M3 (quest database) is complete offline and untested in game.

## 1. Goals and non-goals

**Goals**
- One engine for every faction, race, class and starting zone. Valley of Trials is only the first offline fixture.
- Progress is detected from the character's real state (quest log, completed quests, level, XP, location), never only from a saved step number.
- Recovery from out-of-order play, skips, abandons, unexpected levels and joining mid-route (e.g. a level-25 character).
- Routes are data. Hand-written routes and routes generated by the future Python optimizer use the same format and load without engine changes.
- The UI receives a ready-to-render view and contains no guide logic.
- Fully testable offline with Lua 5.1.

**Non-goals for P2**
- Route optimization itself (P4). P2 only defines the interfaces the optimizer will feed.
- Navigation rendering (arrow, map pins: P3). P2 only outputs targets.
- Automatic quest accept/turn-in (P3, optional, off by default). P2 only exposes "is this quest in the active route".
- No movement or combat automation, ever.

## 2. Architecture

```
          ┌──────────────── offline ────────────────┐
          │ Python optimizer (P4) / hand authoring   │
          │        ↓ writes Guides/*.lua             │
          └──────────────────────────────────────────┘
                              ↓
 Data/*.lua (M3) ──→ RouteCompiler ──→ compiled route (flat steps + segment index)
                              ↓
 WoW events ──→ StateAdapter ──→ CharacterState ──→ Engine.Evaluate ──→ GuideView ──→ UI
   (Compat)       (only WoW-API          (plain table)    (pure Lua,        (plain table)
                   code in P2)                             no WoW API)
                              ↑                ↓
                        SavedVariables ←── GuideMemory (skips, observed facts, timings)
```

| Module | File | Responsibility | WoW API? |
|---|---|---|---|
| Availability | `Guide/Availability.lua` | "Can this character take quest Q now?", mirrors Questie's `IsDoable` rules | no |
| RouteCompiler | `Guide/Compiler.lua` | Merge base route + race start + class overlays into one ordered step list | no |
| RouteSelector | `Guide/Selector.lua` | Choose segment(s) for this character; mid-route joins; segment switches | no |
| Engine | `Guide/Engine.lua` | Evaluate every step's status, pick current/next, recovery, produce GuideView | no |
| StateAdapter | `Core/GuideState.lua` | Build CharacterState from the game; debounce events | **yes** (via `ns.Compat`) |
| GuideMemory | inside Engine, persisted by adapter | Manual skips, observed facts, step timings | no |
| UI | `UI/GuidePanel.lua` (P3 polish) | Render GuideView | yes (frames only) |

**Key rule:** only `StateAdapter` touches the game. Everything else is a pure function of (data, route, state, memory). That is what makes the offline test suite meaningful.

## 3. Data structures

### 3.1 CharacterState (built by the adapter, faked by tests)

```lua
state = {
  time = 1234567,                 -- GetTime()-style seconds, for timings
  faction = "Horde", raceID = 2, classFile = "WARRIOR",
  level = 7, xp = 1240, xpMax = 2000, restedXP = 400,
  map = 1411, x = 43.2, y = 68.5,  -- x/y nil when hidden (instances)
  completed = { [4641] = true, ... },          -- C_QuestLog completed history
  log = {                                       -- current quest log
    [788] = { complete = false, objectives = { { fulfilled = 4, required = 10, finished = false }, ... } },
  },
  bindLocation = "Razor Hill",    -- GetBindLocation(), unverified in Forever (probe)
  knownSpells = { [spellID] = true },  -- only spells routes ask about
  itemCounts = { [itemID] = n },       -- only items routes ask about
  onTaxi = false, isDead = false, isGhost = false,
  skills = { [skillLineID] = rank },   -- professions, for availability
}
```

Fields the probe has not verified in Forever (`bindLocation`, `onTaxi`, `knownSpells`, `skills`) are optional. Steps depending on them degrade to manual confirmation when absent (see 5.3).

### 3.2 Route file format (`Guides/<Faction>/<name>.lua`)

```lua
ns.Guides.Register({
  id = "horde.durotar.1-12",        -- stable, globally unique
  kind = "segment",                  -- segment | start | overlay
  faction = "Horde",
  races = { 2, 8 },                  -- start segments only; nil = all races of the faction
  levels = { 1, 12 },                -- intended range
  entry = { minLevel = 1 },          -- conditions to enter (see 3.4)
  exit = { level = 12 },             -- segment is finished when this holds
  next = { "horde.barrens.12-20" },  -- candidate follow-ups, chosen by the Selector
  source = "hand" | "optimizer@<version>",
  steps = { ... },                   -- see 3.3
})
```

- **start**: race-specific opening (e.g. Valley of Trials for Orc/Troll). One per starting zone.
- **segment**: shared faction route piece, chained by `next`.
- **overlay**: class-specific inserts anchored to steps or levels (3.5).

### 3.3 Step

```lua
{
  id = "vot.t788",                 -- unique within the route; used for skips/timings
  type = "TURNIN",                 -- see section 4
  quest = 788,                     -- quest steps
  objective = nil,                 -- objective index for OBJECTIVE steps
  target = nil,                    -- override; otherwise derived from M3 (start/finish NPC, objective spawns)
  when = { classes = {"WARLOCK"}, minLevel = 10, completed = {...}, notCompleted = {...} }, -- applicability
  optional = false,                -- optional steps never block and are never "returned to"
  group = nil,                     -- alternatives: first applicable/available step of a group is used
  text = nil,                      -- instruction override; otherwise generated from type + data
  note = nil,                      -- extra "why" text shown when expanded
  est = { seconds = 90, xp = 170, src = "E" },   -- estimates with a V/O/E/U label
  tags = { "speedrun" },           -- e.g. speedrun, deathskip, elite, group
  recover = "auto",                -- auto | return | skip (see 6.4)
}
```

All fields except `id` and `type` are optional. Missing targets are derived from M3. Missing estimates are allowed.

### 3.4 Conditions (`when`, `entry`, `exit`)

A small declarative vocabulary, evaluated by the Engine. No Lua functions in route data (the optimizer can't write them, and they can't be validated):

| Key | Meaning |
|---|---|
| `minLevel`, `maxLevel` | character level bounds |
| `races`, `classes` | raceIDs / classFiles |
| `completed`, `notCompleted` | quest ID lists |
| `inLog` | quest ID list |
| `level` | (exit) level reached |
| `xpFraction` | (exit/grind) e.g. `{ level = 12, fraction = 0.5 }` |
| `map` | current uiMapID |
| `spellKnown`, `item` | `{ spellID }`, `{ itemID, count }` |
| `setting` | user setting flag, e.g. `"deathSkips"` |

### 3.5 Class overlays

```lua
ns.Guides.Register({
  id = "overlay.warlock.voidwalker", kind = "overlay", classes = { "WARLOCK" }, faction = "Horde",
  insert = {
    { after = "barrens.t871", steps = { ... } },     -- anchor to a step id
    { atLevel = 10, steps = { ... } },                -- or first step reached at level >= 10
  },
})
```

The compiler applies overlays once, when the class is known, so the executor never branches on class at runtime except through `when`.

## 4. Step types

Every type defines **applicability**, **completion**, **target**, and **recovery**. "Implied done" means a later state already proves it happened.

| Type | Done when | Implied done by | Target | Notes |
|---|---|---|---|---|
| `ACCEPT` | quest in log | quest completed; any later step of this quest progressed | quest giver (M3 START) | unavailable if Availability says no and not in log |
| `OBJECTIVE` | objective `i` finished | quest complete / turned in | objective spawns (M3 OBJ → NPC/object/item sources) | progress = fulfilled/required |
| `COMPLETE` | all objectives finished | turned in | nearest unfinished objective | progress = finished objectives |
| `TURNIN` | quest in `completed` | n/a | finisher (M3 FINISH) | |
| `KILL` | linked quest objective finished | as OBJECTIVE | mob spawns | **standalone kill counts are not supported** (combat log under Midnight restrictions is unverified); KILL must reference a quest objective, otherwise use GRIND |
| `GRIND` | level/XP target reached | n/a | suggested area | target = `{level, fraction}` |
| `GOTO` | within radius of target | any later step done or active with player nearer its target | map/x/y | transitional: never blocks recovery |
| `ZONE` | `state.map` is the target map | later step done | zone entrance | |
| `HEARTH_SET` | `bindLocation` matches | n/a | innkeeper | manual confirm if `bindLocation` unavailable |
| `HEARTH_USE` | arrived at bind location after step became active | later step done | n/a | |
| `FP_LEARN` | node recorded as known | n/a | flight master | known nodes observed from the taxi map (adapter) |
| `FLY` | arrived at destination map/area after being on taxi | later step done | flight master | |
| `TRANSPORT` | arrived at destination map | later step done | dock / zeppelin | boats, zeppelins |
| `TRAIN` | all listed spells known | n/a | class trainer | manual confirm if spell checks unavailable |
| `BUY` | item count reached | n/a | vendor | |
| `DEATHSKIP` | resurrected near the planned graveyard | later step done | death location | optional, requires `setting = "deathSkips"`, shows cost/benefit |
| `ABANDON` | quest no longer in log and not completed | n/a | n/a | speedrun abandon of a quest |
| `NOTE` | player clicks done | n/a | optional | last resort for things the API can't detect |

Class-specific objectives are ordinary steps with `when.classes`. Other verified speedrun strategies are added as new types only after their mechanics are verified in Forever.

## 5. State machine

### 5.1 Per-quest state (single source of truth for quest steps)

```
UNAVAILABLE ──(prereqs met)──▶ AVAILABLE ──accept──▶ ACTIVE ──objectives done──▶ READY ──turn in──▶ DONE
     ▲                              │   ◀──abandon──┘   ◀──abandon──────────────┘
     └──────(exclusive/next-in-chain taken)───┘
```

Derived on every evaluation from `state.completed`, `state.log` and Availability. All quest steps read their status from this, so `ACCEPT`/`OBJECTIVE`/`COMPLETE`/`TURNIN` for the same quest can never disagree.

### 5.2 Step status

| Status | Meaning |
|---|---|
| `DONE` | completion condition holds, or implied |
| `ACTIVE` | applicable, available, not done: the player should do this |
| `WAITING` | applicable but a dependency in this route isn't done yet (normal ordering) |
| `BLOCKED` | a required prerequisite is unmet and **not** scheduled later in the route: needs recovery |
| `UNAVAILABLE` | cannot be done by this character (race/class, exclusive quest taken, quest removed) |
| `SKIPPED` | skipped manually, or optional and passed |
| `UNKNOWN` | can't be evaluated: missing data or an unverified API (never silently treated as done) |

### 5.3 Missing data and unverified APIs

- A step whose completion depends on an unavailable state field becomes **manual-confirm** (the UI shows a "Done" button), never auto-done.
- A step whose target has label `U` shows "location unknown" instead of an arrow; it still completes normally from quest state.
- Estimates carry their label into the view; nothing displays an `E`/`U` value as fact.

## 6. Evaluation and recovery algorithm

Runs on every debounced state change (quest events, level up, zone change; position only when the current step is location-based, at ≤ 2 Hz).

### 6.1 Evaluate

1. Derive quest states for all quests referenced by the compiled route window.
2. Evaluate each step's status in route order. Cost is linear in the window (≈ 100-300 steps), well under 1 ms.
3. **Current** = the first `ACTIVE` step in route order. **Concurrent** = further `ACTIVE` steps that share its area: same hub (target within N yards) or open objectives already in the log. This lets the UI say "accept these 3, then do both objectives".
4. **Next** = the following 3-5 non-done applicable steps.

Because steps are derived from state, the pointer is a result, not an input. The saved step index is only a hint for speed and for "where the player last was".

### 6.2 Out-of-order completion

Covered by "implied done" plus derivation: if 790 is turned in before 788 was accepted, the 790 steps are `DONE` and 788's steps stay `ACTIVE` where they are in the route. Nothing is repeated.

### 6.3 Mid-route join / unexpected levels

On login and whenever `level` > current segment `levels[2]` + tolerance (default 2, tunable):
1. Selector scores candidate segments: faction match, `entry` holds, level within range, and value = remaining achievable XP (`est.xp` of non-done, available steps), discounted by quests that would give reduced XP at the current level. That XP falloff rule must be verified in Forever before it is trusted; until then it is labelled E.
2. If a different segment scores clearly higher, the view shows a **suggestion** ("You're 25: switch to Stonetalon 24-27?"). Auto-switch only if the setting allows it (proposed default: suggest, don't auto-switch).
3. A level-25 first login runs the same selection, so no special case.

### 6.4 Skips and returns

When the current pointer has passed a non-done step (later steps are done):
- `optional` → `SKIPPED`.
- Not optional, and **nothing later in the route depends on it** → `SKIPPED`, logged as a deviation.
- Not optional, and a later required step depends on it (its quest is a prerequisite per M3 `PRE_ALL`/`PRE_ANY`/`availableStartingWith`/`parentQuest` of a later route quest) → added to a **backlog** with the dependent step named ("Needed for *The Barrens Oasis* later"). The engine inserts the return immediately before the first dependent step, unless the step's `recover` is `return` (insert now) or `skip`.
- Manual skips are stored in memory and treated like `optional`.

### 6.5 Abandoned quests

`QUEST_REMOVED` without completion → that quest returns to `AVAILABLE`, its `ACCEPT` step becomes `ACTIVE` again *if* still ahead-relevant (6.4 rules decide), except when an `ABANDON` step planned it.

### 6.6 Zone changes

If the player enters a map where the current step has no target and a later step in the same segment does, the engine advances the "location focus" (GOTO steps are transitional). If no step in the segment matches the map, the Selector offers a segment that does (6.3). It never jumps silently across segments.

### 6.7 Availability and prerequisites

`Availability.lua` mirrors Questie's `QuestieDB.IsDoable` logic (read from Questie source, 2026-11-10):
- completed → not doable; race/class masks (arithmetic test for bits 32/33)
- `preQuestSingle` (PRE_ANY): any one completed. **Questie checks group only when single is absent**; we mirror that.
- `preQuestGroup` (PRE_ALL): every entry completed; a positive entry is also satisfied if any quest in *its* `exclusiveTo` is completed; a **negative entry −X means X must be completed, without the exclusiveTo fallback** (verified in Questie source).
- `nextQuestInChain` completed or active → not doable; `exclusiveTo` any completed or active → not doable
- breadcrumb target completed or active → breadcrumb not doable; active breadcrumb → target not doable
- `disabledByQuest` active, `availableUntilCompleted` completed, `availableStartingWith` neither active nor completed → not doable
- profession / reputation / spell requirements → `UNKNOWN` unless the adapter supplies that state

**Unresolved cases are surfaced, not interpreted:** a negative ID inside `PRE_ANY` (never satisfiable in Questie's logic), a prerequisite missing from the database, or a requirement whose state we don't have → `UNKNOWN` with a reason string. Never assumed satisfied.

**Required M3 schema additions (M3.1):** `breadcrumbs`, `disabledByQuest`, `availableUntilCompleted`, `availableStartingWith`, `requiredMinRep`, `requiredMaxRep`, `requiredSpell`, `requiredSpecialization`, `requiredRanks`. Small, additive changes to `build_data.py` and the schema. Questie's own hidden-quest blacklist lives in the Questie repo, not QuestieDB. Importing it is an open question (8).

## 7. Integration

### 7.1 With M3 data

- Targets: START → NPC/object spawns, FINISH → NPC/object spawns, OBJ → NPC spawns, object spawns, item → drop-source spawns. Nearest spawn to the player wins.
- Labels flow through: a target from an `E` location is shown as approximate; a `U` location shows no arrow.
- Quest names, levels and XP come from M3; route files store only IDs plus overrides.
- Route compile validates every quest ID against M3 and reports missing ones (offline in tests; in game in the probe).

### 7.2 With the UI (GuideView)

```lua
view = {
  route = { id, title, segment = { id, title, levels = {1,12} }, progress = { done = 14, total = 52 } },
  current = {                                 -- primary step + concurrent steps
    { id, type, title = "Turn in Cutting Teeth", detail = "Gornek, inside the Den",
      quest = { id = 788, name = "Cutting Teeth", objectives = {...} },
      target = { map = 1411, x = 42.1, y = 68.3, label = "E", distance = 34 },  -- distance nil if unknown
      progress = { cur = 10, max = 10 }, badges = { "optional", "speedrun", "approx-location" },
      why = "Unlocks Galgar's Cactus Apple Surprise", manualConfirm = false },
  },
  upcoming = { ... },                         -- 3-5 compact entries
  backlog = { { step, reason, dependent } },  -- required returns
  suggestions = { { kind = "segment", to = "...", reason = "..." }, { kind = "deathskip", saves = 180 } },
  warnings = { "3 quests in this segment have unknown turn-in locations" },
}
```

The engine emits `GUIDE_UPDATED` with the view; the UI only renders. Manual actions (skip, confirm, choose suggestion) go back via `ns.Guide.Skip(stepId)` etc.

### 7.3 Persistence (`LevelingNavigatorCharDB.guide`)

`routeId`, active segment id, manual skips, manual confirmations, observed facts (known flight nodes, bind location history), last-step hint, and the step timing log (7.4). **No step index is authoritative.**

### 7.4 Measurement hooks (feeds P4/P6)

On every status transition the engine emits `STEP_DONE {stepId, segmentId, t, level, xp, map, x, y}`. The recorder already stores events; these give per-step and per-segment durations and XP. They are the raw material for route-efficiency measurement (section 9).

## 8. Decisions (2026-11-10)

1. **Segment switches:** suggest only; auto-switch is a user setting, off by default.
2. **Death skips:** opt-in setting `deathSkips`, off by default, shown only with an estimated time saving and its label.
3. **Questie's hidden-quest blacklist:** desirable as a separate labelled layer, but importing it means executing new external Lua (Questie repo). **Awaiting user approval**; until then routes must avoid such quests by authoring.
4. **Recovery tolerance:** 2 levels above a segment's range before suggesting a switch.

## 8a. Shared interfaces (fixed before parallel implementation)

**M3.1 quest fields**, appended after `TRIGGER` in this order (existing indexes unchanged):
`BREADCRUMBS` (list of quest IDs), `DISABLED_BY` (quest ID), `AVAILABLE_UNTIL` (quest ID; `availableUntilCompleted`), `AVAILABLE_WITH` (quest ID; `availableStartingWith`), `MIN_REP` ({factionID, value}), `MAX_REP` ({factionID, value}), `REQ_SPELL` (spell ID; negative = must NOT know), `REQ_SPEC` (number), `REQ_RANKS` (list of {skill, value}).

**Availability API** (`Guide/Availability.lua`, pure Lua):
```lua
local status, reason = ns.Availability.Check(questID, state)
-- status: "COMPLETED" | "ACTIVE" | "AVAILABLE" | "LEVEL_TOO_LOW" | "UNAVAILABLE" | "UNKNOWN"
-- reason: short machine-readable string, e.g. "race", "class", "prereq:788", "exclusive:794",
--         "next_in_chain:794", "breadcrumb_target", "active_breadcrumb", "disabled_by:123",
--         "available_until:123", "available_with:123", "negative_pre_any:-4962",
--         "missing_prereq:2955", "needs_state:skill", "needs_state:rep", "needs_state:spell",
--         "max_level", "no_data"
```
Reads data through `ns.Data.GetQuest` and `ns.DataSchema`; reads `state` per section 3.1 (`completed`, `log`, `raceID`, `classFile`, `level`, optional `skills`, `reputations`, `knownSpells`). Order of checks mirrors Questie's `IsDoable`; level is checked last and only distinguishes `LEVEL_TOO_LOW` (`level < REQ_LEVEL`) from `AVAILABLE`.

**Test harness** (`tools/run_tests.lua`, owned by QA): discovers `tests/*_test.lua`; provides `T.addon(faction, class)` → namespace with `Core/Data.lua`, `Data/*.lua` and `Guide/*.lua` loaded (cached per faction/class), `T.state{...}` → CharacterState with defaults, `T.inject(ns, questID, fields)` → adds a synthetic quest record using schema field names, and assertions `T.eq`, `T.ok`, `T.contains`. Exit code 0 only if all tests pass.

## 9. Route efficiency: measurement before content

Optimizing for "fastest to 60" needs a definition and instruments before writing routes.

**Objective:** minimize total /played seconds from level 1 to 60 for a given (faction, race, class) start, subject to level feasibility.

**Route time model** (per step, summed):
`T = travel + interaction + combat + downtime + waits (respawns, boats) + risk (expected deaths × death cost)`
- travel: path distance ÷ speed (run speed, mount from the level it's affordable; mount rules to verify in Forever). Straight-line distance × a terrain factor until we have real paths.
- combat: kills needed × kill time (level difference, class) + loot. Item objectives use drop rates from QuestieDB drop tables.
- downtime: eat/drink, class-dependent.
- Every term carries a V/O/E/U label. Estimates are replaced by recorder measurements as they arrive.

**Metrics:**
- segment: seconds, XP gained, XP/hour, deaths, deviations
- route: total seconds to 60, time per level, % of time travelling / fighting / idle

**Measurement sources:** engine `STEP_DONE` events + the existing recorder (XP, level, deaths, zone changes, timestamps) → exported via SavedVariables → offline analysis in Python.

**Comparison method:** routes are compared segment by segment between identical boundary states (same level ± tolerance and the same completed-quest set at entry). Baseline = a naive route (all available quests in level order). An optimized route counts as better only when measured, or at least modelled, time is lower *and* the model inputs are labelled. Unverified wins are reported as estimates.

**Optimizer contract (P4):** input = M3 data + measured step costs; output = route files in the format of section 3 with `source = "optimizer@<version>"` and `est` filled. The engine needs no changes to run them.

## 10. Offline testing strategy

Pure engine modules run under Lua 5.1 (`~/wow-tools/lua-5.1.5/src/lua tools/run_tests.lua`) against the real generated `Data/*.lua` and small fixture routes. CharacterState is constructed directly, so no WoW API is needed.

| Area | Test cases |
|---|---|
| Factions / races / starts | each of the 9 starting areas compiles and resolves its first steps for every race and faction; Skyborne (Horde) reports the known data gap instead of failing |
| Classes | every class: overlays applied/ignored correctly; class-specific quests unavailable to other classes; M3 per-class overrides respected |
| Normal progression | accept → objectives → turn in advances without manual input |
| Out of order | later quest turned in first; earlier steps remain, nothing repeated |
| Skipped | optional passed → SKIPPED; required with dependent → backlog + return inserted before dependent |
| Abandoned | quest removed without completion → ACCEPT active again |
| Higher-level character | level 25 with partial history → selector chooses a fitting segment; no low-level steps forced |
| Missing data | U locations, missing prerequisites, negative PRE_ANY → UNKNOWN with reason, nothing auto-done |
| Availability | exclusiveTo, nextQuestInChain, breadcrumbs, negative PRE_ALL semantics |
| Persistence | save memory → reload → identical view; corrupted/old saved data is ignored safely |
| Performance | evaluation of a 300-step window under a set budget (measured offline, re-measured in game) |

Test status will always be reported as **offline-tested** until run in WoW Forever.
